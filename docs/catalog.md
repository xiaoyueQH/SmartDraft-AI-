# 商品管理与下单闭环

入口：`http://127.0.0.1:5183/#/admin/catalog`。管理接口仅管理员可调用，普通用户可浏览上架商品、下单、查询自己的订单并确认取消。

## 操作

**自己的商品**：点击右上角“新增商品”，输入 SKU、名称、说明、售价、初始库存后确认。SKU 为 3～32 位字母、数字、点、横线或下划线，自动规范化为大写且全局唯一。成功后自动切换到已入库目录，后续编辑、上下架、删除、下单和取消均复用现有业务。

1. 搜索“显卡”“显卡 16GB”“机械键盘”等关键词，或选择分类。支持分页；没有匹配时显示空结果，不伪造额外商品。
2. 点击“选择入库”，核对名称、说明和参数。填写本项目销售价格及初始库存，库存默认 0。
3. 点击“确认入库”。在“已入库目录”或普通用户的商品目录中检查结果。
4. 在“已入库目录”编辑名称、说明、售价、可用库存，或上架/下架商品。多人修改或下单后版本已变化，旧编辑返回 409，刷新后重新确认。
5. 普通用户在 `#/products` 选择商品和数量，勾选核对后创建待付款订单；保存购买时的商品快照并扣减可用库存。
6. 在 `#/orders` 预览并确认取消；对应预占只释放一次。
7. 管理员删除商品前勾选确认，商品进入回收站且对用户不可见。历史订单保留；恢复后默认下架，可再手动上架。

固定候选池共 24 款，来源为 `mock_catalog_v1`，覆盖显卡、笔记本电脑、键盘、耳机和显示器。品牌、型号、规格和参考价都是自行构造的模拟数据，未接入淘宝、京东或任何真实商品平台；参考价不表示市场报价。候选不依赖账号密钥、不联网、不自动造业务商品。编辑入库名称不会移除数据库 `is_demo=True` 标志。

## 接口

| 方法 | 路径 | 行为 |
|---|---|---|
| GET | `/api/admin/catalog/candidates` | `q` 最多 80 字符，`category` 分类；返回候选资料、分类、是否已入库 |
| POST | `/api/admin/catalog/imports` | `candidate_id/name/description/price_cents/stock`，确认建立一件商品 |
| POST | `/api/admin/catalog/products` | `request_id/sku/name/description/price_cents/stock`，手动创建自己的商品 |
| GET | `/api/admin/catalog/products` | 管理员查看全部已入库商品，包括原演示商品 |
| GET | `/api/products` | 登录用户查看商品目录，包含本次入库商品 |
| PATCH | `/api/admin/catalog/products/{id}` | 编辑商品；附 `operation_id`、`expected_version` |
| POST | `/api/admin/catalog/products/{id}/state` | 设置 `is_active` 上下架；附操作 ID 与版本 |
| DELETE | `/api/admin/catalog/products/{id}` | JSON body 为操作 ID 与版本，软删除 |
| POST | `/api/admin/catalog/products/{id}/restore` | 从回收站恢复为下架状态 |
| POST | `/api/orders` | `request_id/product_id/quantity/expected_price_cents` 创建本人订单 |

列表每页最多 100 条、offset 最大 10000；实际页面每页 12 条。关键词按空格拆分并同时匹配名称、分类、说明和规格。接口不接受客户端覆盖来源、SKU、商品 ID 或模拟标志。

销售价格为整数分，范围 1～100000000 分；库存为 0～1000000 的整数，拒绝布尔值、浮点数或字符串代替整数。前端按十进制文本直接转换整数分，避免小数计算造成金额偏差。

## 数据与并发

- `products` 保存实际目录字段；`catalog_imports` 保存来源与候选 ID、商品 ID、操作者、时间和原候选快照。原候选快照与编辑后的商品说明分别保留。
- `AsyncEngine → async_sessionmaker → AsyncSession`，每次请求独立短事务。产品与来源审计一同提交，失败或取消回滚。
- 写事务按用户、登录的顺序取得共享行锁，重新检查有效登录、账号状态、密码快照与管理员角色。并行导入允许共享读取，停用/改密/撤销操作会与它互斥。
- 来源和候选 ID 是唯一键；商品 ID 与 SKU 确定性生成。并发重复导入由数据库唯一约束兜底；嵌套事务消化重复冲突后读取首次商品。不会覆盖首次导入结果，也不会重复增加库存。
- 返回 `created=true` 表示本次首次创建，`false` 表示已存在。请求结果不确定时可手动重试同一候选，前端不自动重发或替换候选。
- 复用 HTTP 有界准入与连接池预算；数据库锁等待最多 1.5 秒，忙碌返回可重试 503。候选池在内存只读筛选，不占外部工具或模型预算。

已实现选品、入库、编辑、上下架、软删除、恢复、单商品下单、取消和[演示履约与整单退货退款](fulfilment.md)。真实采购、支付、购物车和换货尚未实现。产品名和卡片去除重复的“模拟”标签；仅页面统一说明演示环境。数据库仍保存真实来源与演示标志。

## 生命周期与写入保护

- `products.is_active/deleted_at/version` 决定上架、回收站与乐观版本。普通用户查询仅返回上架且未删除的商品。
- 管理操作按用户、登录、商品顺序加锁。`product_changes` 与商品修改同事务保存，包含操作者、操作、指纹、结果快照与时间；操作 ID 按账号和商品隔离。相同 ID/参数重试返回原结果，不同参数返回 409。
- 修改价格和可用库存要求预期版本；下单、取消和显式演示预占脚本每次调整库存都会递增版本，防止后台旧表单覆盖库存。SKU 与数据来源不能通过编辑接口改写。
- 删除只移入回收站，保留原商品、来源和订单外键。重复入库回收站商品会提示先恢复，不能靠重试导入绕过删除状态。
- 下单按用户、登录、商品顺序加排他锁。一次只购买一种商品，1～99 件；检查当前上架状态、价格、库存与金额上限。订单、购买快照、库存预占、库存扣减同事务提交，没有任何真实支付动作。
- `request_id` 在账号内唯一；同请求重试返回原订单，即使该订单后来已取消也不创建第二笔。原请求改参数会冲突；另一账号使用相同 ID 不会读取该账号的订单。
- 下单响应前事务已提交。网络结果未知时保留原请求 ID，只允许手动重试；下单或管理写入未确认时，页面锁定会打断当前请求的商品切换、刷新和翻页。

## 手动新增与弹窗

手动商品保存 `CatalogImport.source=manual`、操作者、原始输入和请求指纹，商品 `is_demo=False`；内置候选仍保存 `mock_catalog_v1` 来源。商品来源和交易环境是两个概念：手动商品可正常下单和取消，订单继续保留演示标志，不发起支付。取消校验依赖订单、明细与真实库存预占，不再要求商品来源标志等于订单的交易环境标志。

手动创建使用账号范围的 request_id 和规范化参数指纹防重。相同请求相同参数返回原商品；不同参数返回 REQUEST_REUSED，SKU 重复返回 SKU_EXISTS；回收站商品返回 PRODUCT_DELETED。产品和来源审计同事务写入，无新存储或重复依赖。

新增、候选入库均使用原生 dialog，焦点与背景由浏览器隔离，稳定滚动条槽保留网格宽度。弹窗打开不会改变卡片列数、尺寸或位置；关闭后返回原按钮，并避免主动滚动。失败保留表单，明确 4xx 可修改输入；结果未知则冻结输入和关闭，原请求体可手动重试。

Chrome 实测：1707×893 视口下打开候选入库弹窗，前三张卡片坐标、尺寸、网格列数和页面滚动位置均相等；390×844 下新增商品弹窗未越出视口，Esc 正常关闭，临时视口已恢复。自有商品 OWN-DISPLAY-A27 录入、下单、取消通过，库存 12 → 11 → 12。新增 13 项后端和 3 项前端测试，全量后端 126 项、前端 46 项通过，Luna 复审通过。

## 验证

新增测试涵盖越权、输入范围、伪造来源、空搜索、分页、入库可见性、重复导入、事务内失效身份检查、失败回滚和前端金额/重复提交/旧响应/卸载取消。真实 PostgreSQL 的独立测试 schema 中，两个管理员同时发起 24 次同候选导入，只有一次创建、一个来源记录，初始库存保持不变。这是该业务的并发正确性验收，不代表生产系统的吞吐能力。

生命周期新增 API 闭环测试，以及真实 PostgreSQL 的超卖竞争、两个管理员修改竞争和审计失败回滚测试。两个账号同时发起 12 次下单竞争 3 件库存，只有 3 笔成功，重试成功请求也不重复预占。前端测试涵盖明确确认、原请求重试、下单时禁止切换商品，以及管理写入未确认时锁定其他行。全量后端 113 项、前端 43 项通过；类型检查和构建通过；GPT-5.6 Luna 复审指出的两处前端竞态已修复并通过复审。
