# 验证指南

## 按改动范围验证

先确定要验证的行为，再运行对应检查。通过且代码未变化时不重复执行；有新失败或实质修复才复测相关路径。真实模型、浏览器及并发测试分别说明条件，不能互相替代。

| 改动           | 优先检查                                                                 |
| -------------- | ------------------------------------------------------------------------ |
| 纯文档         | 本地链接、Mermaid语法、实际节点与图一致、模拟/实测分区                   |
| 沟通及来源     | test_consultation、test_advisor、test_drafting                           |
| 文档审查及历史 | test_document_review；前端document-review.test，含真实PG并发应用与HITL恢复 |
| 起草及恢复     | test_draft_sections、test_draft_graph、test_draft_quality、test_drafting |
| 模型工厂/配置  | test_model_factory、test_config                                          |
| 项目状态机     | test_projects、test_projects_postgresql、test_agent_tools                |
| 登录与账号切换 | test_auth、test_security，相关前端会话测试                               |
| 缓存/并发      | test_cache、test_admission、test_postgresql及对应实际服务检查            |
| 后台接待待办   | test_support_inbox，frontend/tests/admin-projects.test；失败更新、时限配置、分页与角色校验 |
| 前端交互       | 对应SFC/组件测试，必要时类型构建与一次浏览器复测                         |

测试文件在[tests](../tests)，前端测试在[frontend/tests](../frontend/tests)。没有向量RAG或旧电商运行路径，不恢复已删除的旧测试入口。

## 本地自动检查

使用Conda环境，命令从仓库根执行。以下是完整检查参考，日常按影响范围选择，不必每次全部运行。

```powershell
conda activate D:\code\env\supportflow
$env:SUPPORTFLOW_TEST_POSTGRES="1"
$env:SUPPORTFLOW_TEST_REDIS="1"
python -m pytest -q
python -m ruff check backend scripts tests
python -m ruff format --check backend scripts tests
Set-Location frontend
npm test
npm run format:check
npm run build
```

PG/Redis真实集成依赖已启动的本机服务及有效配置。不启用相应环境变量时会跳过部分测试；有skip的结果不能写成“真实集成已全部验证”。测试使用临时schema和随机缓存前缀，只清理自身数据，不执行FLUSHDB或删除正式业务表。

## 浏览器执行清单

人工接待专项：`python -m pytest tests/test_human_conversation.py -q`；启用 `SUPPORTFLOW_TEST_POSTGRES=1` 可验证真实PG消息并发及历史迁移，使用独立schema。前端覆盖人工求助、待交接时发送、管理员身份和历史检索。浏览器以独立客户记录测试：文字/按钮求助、后台提示、接管、双向消息、后台纪要、原话查询、转交/恢复AI。严格“正在执行”的接管时序需用事件阻塞模型结果断言，不能依赖随机响应延迟。模型失败时反复打开页面不得循环付费请求；原话和人工发送仍须保留。

异常与并发接待专项：`python -m pytest tests/test_recovery_acceptance.py tests/test_flow_recovery.py -q`。前者覆盖两个管理员同时接管、同请求并发重试、超时与人工回复/只等人工同时发生、多个恢复实例派发、两个客户同时运行真实业务图的状态隔离，以及需求写作中接管。数据库并发使用临时schema；时序测试的模型响应由事件控制，不冒充真实供应商延迟。锁冲突回归需实际更新用户外键，确保触发KEY SHARE检查；只更新普通项目字段不足以证明避免了原死锁。

断线浏览器验收前确认无其他活动执行，再短暂停止本地API：输入区保留待确认消息，恢复后点“原请求重试”，数据库只出现一条原话。空响应、代理错误页、截断成功响应需显示中文提示并保留未知结果的原请求，不能把解析失败当成明确业务失败、用新编号再次发送。前端相关用例在`frontend/tests/auth.test.mjs`。

流式改动定向检查：`python -m pytest tests/test_model_factory.py tests/test_streaming.py -q`；前端在frontend下执行`node --test tests/auth.test.mjs tests/conversation-panel.test.mjs tests/projects-view.test.mjs`。检查首段在模型结束前可见、工具参数与推理不外发、碎片UTF-8、取消释放名额、流内到期续期、账号切换、断线订阅原run及最终消息不重复。真实模型延迟与供应商能力需另用一次独立记录验证，不以模拟替代。

1. 选一个独立的沟通记录，不编辑现有客户基线；保留记录编号和开始条件。
2. 输入业务与部分技术约束，要求先沟通，验证没有提前起草。
3. 补充关键规则并明确要求生成，观察真实执行及来源标记。
4. 检查详细程度：角色、功能、字段、接口、状态、异常、并发、技术、部署及验收。
5. 对照用户原话，检查已指定选择、自动补充、排除项和待确认是否分开。
6. 刷新后检查同一run和同一文档，不重新发送生成请求。
7. 需要验证评审时，分别检查提交、客户/负责人确认、编辑重置签名、V1及正文锁定。
8. 撤回和驳回分别由创建者与负责人执行，不能把两者当作同一操作。
9. 记录原始失败及修复后的结果，截图、正文、日志分开保存。
10. 独立测试记录及时移入可恢复回收站；用户明确保留供审阅的草案按其要求保留。

不为了测试而自动审批真实客户需求。人工修订稿可以用于状态机验收，但不能当作模型原始输出质量通过的证据。

## 模拟、自动检查和真实验收

| 类型                | 能证明什么                           | 不能证明什么                   |
| ------------------- | ------------------------------------ | ------------------------------ |
| 文档模拟            | 理解合法执行与边界                   | 模型一定选择该顺序             |
| 确定性单元/集成测试 | 权限、事务、预算、状态与已建回归行为 | 所有真实业务语义正确           |
| 真实PG/Redis检查    | 当次隔离环境中的并发/持久化行为      | 生产固定QPS、所有硬件性能      |
| 真实模型生成        | 该样本的工具选择、输出与错误         | 所有输入都完整正确             |
| 浏览器流程          | 页面交互、角色、保存与展示           | 未实际执行的外部接口或开发成果 |

模型返回完整草案后，应独立检查语义与工程可实施性。来源引用存在不等于摘要含义必然正确；【自动生成】存在也不等于默认规则合理。

## 审查与证据

按仓库要求使用GPT-5.6 Luna、medium做一次主审；修复后只定向复核相关问题。纯文档变更不要求重启API或再次付费调用模型。

证据放Git忽略的storage/verification，注明日期、配置范围、动作、失败、最终结果及清理情况。验收文档只引用已存在的历史证据，不把不同代码版本的通过数量相加成一次最新全量结果。当前证据与问题见[验收记录](验收记录.md)。

## 文档审查验收

使用独立测试项目，设置客户明确的权限要求，并在正文加入相反描述、取消状态约束错误。手动检查后确认原稿未变，候选差异有精确依据；应用后版本递增、确认清空且旧稿可恢复。等待中编辑正文应拒绝过期候选；同一请求重放不重复应用，不同用户不能读他人检查记录。

真实模型结果不保证发现全部错误；报告须如实标明未读块、未修问题或验证失败。自动测试模型替身只验证业务边界，真实SQL正确性需另行执行数据库测试，不能由模型结论替代。
