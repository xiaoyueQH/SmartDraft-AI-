# 服务器部署与演示

适用于小范围演示的Linux服务器、同机Nginx/API/Worker。下面是待应用的部署步骤及模板，不表示已经远程配置或验收了服务器。实际项目目录、系统服务名称、域名/IP和证书路径需按服务器填写；先备份现有Nginx配置，不覆盖其他站点。

## 公网HTTP为何报错

`crypto.randomUUID`与Web Locks只在浏览器安全上下文中提供。公网`http://IP`不满足条件；本机localhost通常属于可信例外，所以本地正常、搬到服务器后才暴露。人数、数据库连接数、是否更新浏览器不能把公网HTTP变成安全上下文。

前端现通过同一requestId函数生成请求编号：优先randomUUID，不存在时用getRandomValues安全随机字节生成UUID v4。不会用Math.random、时间戳代替。此兼容修复解决编号异常，**不意味着公网HTTP登录续期已解决**；Web Locks保护继续保留，不能用localStorage模拟锁或取消续期互斥。

外部演示推荐浏览器可信的HTTPS。有域名可用域名证书；只有公网IP也可用受信任IP证书，不必为了演示关闭浏览器保护。

## HTTPS部署顺序

1. 保持API绑定127.0.0.1:8091，PostgreSQL/Redis仅回环开放。浏览器访问Nginx的443，前端和/api同源，不直接公开8091/15432/16379。
2. 完成证书校验、配置HTTPS后，构建frontend/dist并交给Nginx托管。小范围演示也不必把Vite开发服务器暴露公网。
3. 修改本机.env的来源与Cookie配置。只保留实际使用的来源，不写通配符，不把密钥放进前端变量或仓库。
4. 无活动任务时重启API/Worker使配置生效；检查就绪和浏览器安全上下文。

### 先提供证书验证入口

安装Certbot时使用官方对应操作系统的步骤；IP证书webroot方式要求Certbot至少5.4。确认版本：

```bash
certbot --version
sudo mkdir -p /var/www/certbot
```

把下面location加入服务器现有80端口站点，保留其他配置。首次还没有证书时，不要直接启用引用不存在证书文件的443块。

```nginx
location ^~ /.well-known/acme-challenge/ {
    root /var/www/certbot;
    try_files $uri =404;
}
```

如果尚无站点，可临时建一个只服务该验证目录、其他路径返回404的80端口server。按系统的sites-enabled或conf.d惯例启用；用nginx -t通过后再reload。公网防火墙/云安全组允许证书验证的80端口及最终使用的443端口。

### 有域名时

将域名解析到服务器，使用真实域名替换示例。先确认HTTP验证目录能从公网访问，再请求证书：

```bash
sudo certbot certonly --webroot --webroot-path /var/www/certbot \
  --cert-name supportflow -d demo.example.com
```

### 只有公网IP时

以下203.0.113.10是文档示例，必须替换为真实公网IP，不要原样申请。

```bash
sudo certbot certonly --webroot --webroot-path /var/www/certbot \
  --preferred-profile shortlived --cert-name supportflow \
  --ip-address 203.0.113.10
```

这是正式受信任证书请求；若加--staging只用于验证签发过程，所得测试证书不能作为浏览器最终验收。IP证书约6天有效，必须启用自动续期及续期后的Nginx重载。不要把需要手动忽略证书警告的自签名证书当成完成。

### 启用Nginx与应用配置

复制并按实际地址修改[HTTPS模板](../docker/nginx.conf.example)，其中server_name使用域名或IP，root指向实际frontend/dist。示例证书名固定supportflow，与前面Certbot命令一致；若已有该证书名，先用certbot certificates核对，避免误用其他站点证书。模板应放在Nginx的http上下文中，不能直接替换整个主nginx.conf。

模板保留原Host和请求来源、转发/api到8091、关闭流式响应缓冲及自动上游重放。API目前通过路径/api提供服务，proxy_pass不能去掉/api前缀。模板假设Nginx直接面向浏览器；如果前面还有负载均衡，需要另行核对可信代理和真实来源，不盲目信任外部转发头。

应用.env示例，有域名时把IP示例改为域名。这里不包含数据库密码和模型密钥：

```dotenv
SF_APP__HOST=127.0.0.1
SF_APP__PORT=8091
SF_APP__TRUSTED_PROXY_IPS=127.0.0.1
SF_AUTH__COOKIE_SECURE=true
SF_AUTH__ALLOWED_ORIGINS=["https://203.0.113.10"]
```

默认443来源不带端口；用非默认端口则必须写实际端口。localhost开发入口只在确有需要时另外保留，HTTP来源不能替代HTTPS来源。API和Worker使用同一配置及持久签名密钥，修改配置后两个进程都需重启；不要在生成或检查执行中强制终止。

API沿用`python scripts/start_api.py`入口。该入口启用Uvicorn代理头处理，只信任配置中的本机Nginx，因此客户端IP限流和HTTPS来源才能正确识别。不要改成未设置这些参数的直接uvicorn启动命令，也不需要在应用中重复套一层代理中间件。

```bash
cd /srv/supportflow/frontend
npm ci
npm run build
sudo nginx -t
sudo systemctl reload nginx
```

路径按实际克隆位置替换，并确保Nginx有只读dist的权限。若已有API/Worker由systemd或其他工具管理，沿用实际服务名称；不要额外启动重复Worker。部署新前端只需替换构建产物并刷新页面，旧打包文件不会自动获得代码修复。

为Certbot配置自动续期和deploy-hook，续期成功后执行`nginx -t && systemctl reload nginx`。验证现有定时任务已启用，并按官方文档执行一次renew --dry-run；IP证书不适合依赖人工每周续签。

## 临时不配置证书的受控演示

只有少量受信任演示人员、且他们本来就有SSH权限时，可各自在自己的电脑建立本地转发，浏览器仍访问localhost：

```bash
ssh -N -L 15183:127.0.0.1:80 你的SSH用户@服务器公网IP
```

浏览器打开`http://127.0.0.1:15183/#/`。假设服务器现有Nginx在80端口提供同源前端及/api；如实际端口不同，调整转发目标。必须在允许来源中加入`http://127.0.0.1:15183`；若Nginx按域名分虚拟站点，还需确认回环Host命中本应用。这个临时HTTP回环方案不要开启Secure Cookie；若主站已启用HTTPS/Secure Cookie，使用正式HTTPS入口。

此方案没有把公网HTTP变成安全连接，而是浏览器访问自己的回环地址、跨网络由SSH加密。不要为了演示给所有人共用服务器管理员账号；没有既有SSH权限的访客优先使用HTTPS。

## 演示前验收

在外部浏览器的HTTPS页面检查：

```javascript
window.isSecureContext       // true
typeof crypto.randomUUID    // "function"
typeof navigator.locks      // "object"
```

这些仅是浏览器能力检查，不读取任何凭证。随后实际验证密码登录、刷新继续登录、两个标签页续期不互相撤销、创建沟通、发送一条请求、断线查看原任务及退出。业务模型质量与生产吞吐仍单独验收；两三人演示不能证明固定并发容量。

接口检查：/api/health/ready与/api/health/worker均应ready。证书、来源或Cookie修改前的登录可能需要重新登录，不要以旧HTTP会话残留作为HTTPS失败判断。
